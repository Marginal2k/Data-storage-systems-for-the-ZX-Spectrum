# Opus Discovery: работа с диском из машинного кода

Процедуры для адаптации игр и программ к дисковой системе Opus Discovery:
чтение и запись секторов и логических блоков, загрузка и сохранение файлов по имени,
моноблочный загрузчик (аналог однофайловых загрузчиков TR-DOS), а также
инструменты для сборки образов `.opd` и автоматического тестирования в ZX-M8XXX.

```
src/opuslib.asm     библиотека (sjasmplus), не зависит от версии ПЗУ
src/mono.asm        моноблочный загрузчик на базе библиотеки
src/monotiny.asm    минимальный моноблочный загрузчик (~290 байт с таблицей)
tools/opdtool.py    образы .opd/.dsk (SD и DD): создание, каталог, файлы, токенизатор BASIC
tools/dskinfo.py    разбор CPCEMU .dsk: ID секторов в физическом порядке
tools/mkmono.py     сборка моноблока: BASIC-загрузчик + блоки кода в одном файле
tools/zxharness.py  управление ZX-M8XXX через headless Edge (CDP)
tests/              автотесты (библиотека, моноблок, сквозной пример)
examples/demo/      пример: экран + код, автозапуск по RUN
```

## 1. Что берётся из ПЗУ (одинаково во всех версиях)

Проверено побайтно в v1.2, v2.2, v2.22, EXCOM 2.28 и QuickDOS 2.31:

| Адрес | Назначение |
|---|---|
| `CALL #1708` | подключить ПЗУ Opus; все регистры сохраняются |
| `CALL #1748` | отключить (там `RET`, флаги и регистры сохраняются) |
| `#0066` | вектор NMI = `JP (HL)`. DRQ контроллера заведён на NMI: на каждый байт сектора приходит NMI, поэтому всё время обмена HL должен указывать на ваш обработчик |

Всё остальное библиотека делает сама, через регистры WD1770 и PIA MC6821.
Поэтому от версии ПЗУ она не зависит: ни таблиц переходов `RST #30`, ни служебных
переменных ПЗУ она не использует.

Пока Opus подключён, область `#0000-#3FFF` занята ПЗУ, RAM и портами Opus.
Код, буферы и стек должны лежать от `#4000` и выше.

**Регистры** (в памяти, а не в портах):

| Адрес | Чтение | Запись |
|---|---|---|
| `#2800` | статус | команда |
| `#2801` | дорожка | дорожка |
| `#2802` | сектор | сектор |
| `#2803` | данные | данные |
| `#3000` | порт A PIA | b0/b1 — выбор дисковода 1/2, b4 — сторона, b5 — FM (0 = MFM), b7 — режим джойстика |
| `#3001` | управление A PIA | b2=1 → по `#3000` доступен регистр данных (ПЗУ хранит в b0/b1 свои флаги) |

## 2. Формат диска

Геометрия **не фиксирована**. ПЗУ при каждом обращении читает якорный сектор
(дорожка 0, сторона 0, сектор 0 = блок −1) и берёт из него байт 2 = дорожек,
байт 3 = секторов на дорожке, байт 4 = флаги (b7–6 размер сектора: 01=256, 10=512,
11=1024; b5 = FM; b4 = две стороны). На практике встречаются:

| | дорожек × сторон × секторов × байт | флаги | объём | каталог |
|---|---|---|---|---|
| «SD» (стандарт Opus) | 40 × 1 × 18 × 256 | `#40` | 180 КБ | блоки 0–6 (112 записей), у форматтера DJr 0–4 |
| «DD» | 80 × 2 × 10 × 512 | `#90` | 800 КБ | блоки 0–6 (224 записи) |

Оба физически MFM 250 кбит/с. «SD/DD» здесь — названия Opus, а не FM/MFM.

- Номера секторов идут с 0. **Логический блок = один сектор любого размера.**
- **Логический блок B** (так считает ПЗУ, подпрограмма с адреса `#11DA` в дизассемблере):
  `real = B+1; сектор = real mod SPT; t = real div SPT; дорожка = t mod TPS; сторона = t div TPS`.
  На двустороннем диске **сначала заполняется вся сторона 0**, потом сторона 1
  (на DD граница сторон — блок 799).
- Каталог занимает блоки 0..N, где N — «последний блок» в записи 0. Записи по 16 байт:
  `DW байт_в_последнем_блоке−1, DW первый_блок, DW последний_блок, DS 10 имя`.
  Запись 0 — метка диска (блоки 0–6). Файлы непрерывны и отсортированы по первому блоку.
  Маркер конца: первый блок = число блоков диска, последний = `#FFFF`.
- Файл начинается с 7-байтного заголовка: `тип, длина, параметр1, параметр2`
  (BASIC: автостарт и длина программы; CODE: адрес и `#8000`).
- Физический порядок секторов, который пишет форматтер ПЗУ: **шаг +7**.
  SD: 7, 14, 3, 10, 17, …, начало каждой следующей дорожки сдвинуто на 1.
  DD: 7, 4, 1, 8, 5, 2, 9, 6, 3, 0, начало чередуется 7/2 (так в реальном образе
  из FuseX). Чтение по порядку номеров занимает около `шаг` оборотов на дорожку,
  в физическом порядке — около одного оборота. (В Section 4 указан шаг 11 — это
  неверно, правильное значение дают таблица у ван Донгена и реальный DSK.)

## 3. Библиотека `src/opuslib.asm`

```asm
        DEFINE OD_BUF #7E00     ; буфер на сектор для Opus БЕЗ RAM (необязателен)
        INCLUDE "opuslib.asm"
```

**Точность.** Обработчики NMI считают байты в BC. Чтение кладёт в память ровно
запрошенное число байт, а остаток сектора принимает у контроллера и выбрасывает.
Поэтому за концом файла или блока не пишется ни байта, даже временно, и отдельный
буфер на 512 байт для этого не нужен. `od_load` и `od_save` не трогают память
вне файла вообще: первый блок (с 7-байтным заголовком) идёт через `OD_BUF`.

**Тайминг (реальное железо).** Байт приходит раз в 32 мкс = 112 тактов. Обработчик
NMI на чтение занимает около 84 тактов. В `#4000-#7FFF` ULA во время вывода экрана
растягивает выполнение, и байт может быть потерян (эмулятор этого не моделирует).

**RAM Opus.** На большинстве Opus стоит опциональная 2К RAM (`#2000-#27FF`), которая
видна только пока Opus подключён, то есть ровно тогда, когда идут NMI. Все пять версий
ПЗУ используют из неё только `#2000-#208F` (таблицы, их трогать нельзя: по ним
работает обработчик прерываний ПЗУ на `#0048`) и `#2780-#27FF` (код якорного сектора).
Проверено в эмуляторе: `tests/probe_opusram.py`. Каждый вызов `od_init` проверяет,
есть ли RAM: пишет два разных байта в `#26FE/#26FF`, читает и восстанавливает.
Если RAM есть:
- обработчики NMI копируются в `#2100`, и **библиотека может лежать где угодно**,
  в том числе в тормозящей памяти: по времени критичен только обработчик;
- буфером на сектор служит `#2200` (1 КБ), и **память Spectrum под буфер не нужна**.

Если RAM нет, обработчики работают из кода библиотеки (тогда на реальном железе держите
её выше `#8000`), а буфером служит `OD_BUF`. Если не задан и он, файловые процедуры
возвращают CY, A=`#FE`. Отключить использование RAM: `DEFINE OD_ORAM 0`.

Файловые процедуры работают целиком при подключённом Opus (буфер в RAM Opus виден
только так): `od_find`, `od_load`, `od_save`, `od_geom` — это обёртки, которые
подключают Opus, вызывают внутренние `..._in` и отключают его.

Настройка (через `DEFINE` до `INCLUDE` или `sjasmplus -DИМЯ=значение`;
**`IFNDEF` в sjasmplus видит только DEFINE, а не метки через `=`**):

| Параметр | По умолчанию | |
|---|---|---|
| `OD_ORAM` | 1 | использовать RAM Opus, если она есть |
| `OD_FAST` | 1 | 1 = чтение/запись в физическом порядке (шаг определяется сам двумя командами Read Address), 0 = по порядку номеров |
| `OD_SAVE` | 1 | включить запись (`od_write`, `od_wsec`, `od_save`) |
| `OD_FILES` | 1 | включить `od_find`, `od_load` (и `od_save`) |
| `OD_RATE` | 0 | скорость шага головки: 0..3 = 6/12/20/30 мс |
| `OD_RETRY` | 6 | повторов на сектор |
| `OD_TOUT` | 3 | таймаут команды, единицы ≈ 1,1 с |
| `OD_TPS0` | 40 | начальное `od_tps` (дорожек на сторону) |
| `OD_SPT0` | 18 | начальное `od_spt` (секторов на дорожке) |
| `OD_SPG0` | 1 | начальное `od_spg` (размер сектора / 256: 1, 2 или 4) |
| `OD_MAXSPT` | 24 | максимум секторов на дорожке для быстрого чтения |

Геометрию задайте одним из двух способов: вызовите `od_geom` (прочитает якорный
сектор, как это делает ПЗУ) или запишите `od_tps`/`od_spt`/`od_spg` сами.
`OD_BUF` (`DEFINE`, а не метка) должен вмещать один сектор самого большого
используемого размера (для DD — 512 байт).

Размеры: всё вместе — 1589 байт (`OD_FAST=1`) или 1227 (`OD_FAST=0`);
без записи — 1441 / 1079; только чтение блоков — 1037 / 675
(без поддержки RAM Opus, `OD_ORAM=0`, минимальная сборка — 592).

### Высокий уровень (сами подключают и отключают Opus, возвращаются с DI)

| Процедура | Вход | Выход |
|---|---|---|
| `od_read` | HL = первый блок, B = число блоков (1..255), DE = адрес; `od_tail` = сколько байт взять из последнего блока (0 = весь) | NC = успех; CY = ошибка, A = статус. `od_tail` обнуляется |
| `od_write` | то же | то же; при защите от записи бит 6 в A |
| `od_find` | HL → имя (10 символов, дополненное пробелами) | NC: HL = первый блок, DE = последний, A = байт в последнем −1 |
| `od_load` | HL → имя, DE = адрес (0 = из заголовка) | NC: HL = длина, DE = адрес, A = тип |
| `od_save` | HL → имя, DE = адрес, BC = длина | перезаписывает **существующий** файл на месте (слот сохранения), каталог не меняется; CY + A=`#FF` — если файл мал |
| `od_geom` | (дисковод = `od_unit`) | NC: A = флаги якоря; выставлены `od_tps`, `od_spt`, `od_spg` |
| `od_rload` | HL → имя, DE = адрес | «сырой» файл: NC: HL = длина (из каталога), DE = адрес; пишет ровно `[адрес, адрес+длина)` |
| `od_rsave` | HL → имя, DE = адрес, BC = длина (1..65535) | «сырой» файл: есть и хватает места — перезаписывается на месте, длина в каталоге обновляется (лишние блоки освобождаются); нет — **создаётся** в первой подходящей дыре. NC: HL = первый блок. CY: A=`#FF` файл мал, `#FD` нет места, `#FC` каталог полон |

Переменные: `od_unit` — дисковод (1/2), `od_tps`, `od_spt`, `od_spg` — геометрия.

`od_load` пишет ровно `[адрес, адрес+длина)`. `od_save` память только читает:
для неполного последнего сектора на диск уходит то, что лежит в памяти после
данных, но сама память при этом не меняется.

**«Сырые» файлы** (`OD_RAW`, по умолчанию включено; запись ещё и при `OD_SAVE`).
Вся служебная информация о файле лежит только в каталоге: первый и последний блок
и число байт в последнем блоке. 7-байтового заголовка нет, данные начинаются
с первого байта первого блока. Экран 6912 байт занимает ровно 27 блоков по 256
(с заголовком было бы 6919 байт = 28 блоков) или 14 по 512.

ПЗУ такие файлы показывает в каталоге, но не загружает: первые байты оно примет
за заголовок. Работать с ними можно только этими процедурами или `opdtool.py`
(`OPD.add_raw`).

`od_rsave` при создании вставляет запись в каталог по порядку блоков и сдвигает
следующие записи на одно место. Сдвиг идёт блок за блоком каталога через один
секторный буфер, весь каталог в памяти не нужен. Место в каталоге проверяется
заранее, поэтому при «каталог полон» диск не меняется. `od_find` теперь также
оставляет `od_flast` (байт в последнем блоке −1, слово) и `od_fcblk` (блок
каталога с записью).

### Низкий уровень (Opus уже подключён вызывающим, DI)

| Процедура | |
|---|---|
| `od_init` | при необходимости настраивает PIA; принимает дисковод и регистр дорожки, оставленные ПЗУ |
| `od_select` | A = дисковод, C = сторона; для каждого дисковода хранит свой регистр дорожки |
| `od_restore`, `od_seek` (D = дорожка) | seek с проверкой; при ошибке — restore и повтор |
| `od_rsec`, `od_wsec` | B = дорожка, C = сектор, DE = буфер, `od_cnt16` = байт (0 = весь сектор); проверяют, что передано всё |
| `od_b2p` / `od_p2b` | логический блок ↔ дорожка/сектор/сторона |
| `od_cmd` | A = команда; ждёт окончания с таймаутом; A = статус. BC/DE/HL не трогает: они принадлежат обработчику NMI |

## 4. Моноблок (как в TR-DOS)

На диске один BASIC-файл. Длина в его заголовке — это длина только BASIC-части,
а запись каталога покрывает BASIC и все блоки кода, которые идут следом.
На диске каждый блок начинается с границы сектора, а в память грузится **побайтно
точно**: последний сектор блока обрезается до реальной длины (экран 6912 байт на
DD — это 13,5 сектора, загрузится ровно 6912 байт, `#5B00` не тронут):

```
10 REM <загрузчик>
20 CLEAR n: RANDOMIZE USR (PEEK 23635+256*PEEK 23636+5)
```

**Как загрузчик находит, где продолжать.** Проверено на всех пяти ПЗУ: после того как
ПЗУ загрузило BASIC (`RUN` или `LOAD *"m";1;"run"`), в регистрах WD1770 остаются
дорожка и сектор **последнего прочитанного сектора BASIC-части**, а в PIA — выбранные
дисковод и сторона. Загрузчик продолжает со следующего сектора, как в TR-DOS через
`23796`. Так работает и на границе дорожки, и на стороне 1, и при копировании файла
на любое место диска.

Запасной режим `--catalog`: загрузчик ищет своё имя в каталоге и не зависит от
того, что ПЗУ сделало последним. Стоит около 250 байт и чтения каталога.

```bash
python tools/mkmono.py game.opd --block screen.scr@16384 --block game.bin@24576 --start 32768
python tools/mkmono.py game.dsk --fmt dd --block ... --start 32768     # DD, .dsk для Fuse
```

Геометрия берётся из образа (`--disk`) или из `--fmt` и зашивается в загрузчик:
BASIC-часть и блоки выравниваются по размеру сектора диска.

| Ключ | |
|---|---|
| `--block файл@адрес` | блоки загружаются в указанном порядке |
| `--start A` | переход после загрузки (0 = возврат в BASIC) |
| `--sp A` | установить SP перед переходом |
| `--clear N` | CLEAR в строке 20 (по умолчанию «наименьший адрес − 1», если он > 24000) |
| `--tiny [--step 7]` | минимальный загрузчик `monotiny.asm` (~360 байт со всей обвязкой); шаг должен быть взаимно прост с числом секторов |
| `--compact` | библиотечный загрузчик с последовательным чтением (~660 байт) |
| (по умолчанию) | библиотечный загрузчик с быстрым чтением (~1020 байт) |
| `--org A` | куда переносить тело загрузчика; по умолчанию выбирается само (см. ниже), `0` = оставить в REM |
| `--reserve A-B` | память, которую загрузчику занимать нельзя (можно несколько) |
| `--catalog [--buf A]` | поиск позиции по каталогу; буфер на один сектор (по умолчанию — адрес первого блока, он всё равно будет перезаписан) |
| `--fmt sd`/`sdds`/`dd` | формат нового образа |
| `--name run` | имя файла; `run` загружается по `RUN` |
| `--disk base.opd` | добавить в существующий образ вместо нового |
| выходной `.dsk` | CPCEMU-образ с раскладкой секторов как у ПЗУ (для Fuse) |

**Где работает загрузчик.** Обработчик NMI загрузчик при наличии RAM Opus переносит
туда, как и библиотека. На случай Opus без RAM 15-байтная перемещаемая заглушка в REM
копирует тело в свободную **нетормозящую** память: самый верхний участок в `#8000-#FFFF`, который
не занят ни одним блоком, стеком под `CLEAR` (512 байт), UDG (если возвращаемся в
BASIC) и зонами `--reserve`. Сборщик печатает выбранный адрес. Если такого места
нет, тело остаётся в REM (`#5CDF`), и печатается предупреждение (см. «Тайминг»).
Блоки, перекрывающие сам BASIC-загрузчик, тоже дают предупреждение.

Ограничения:
- Память, куда встаёт тело загрузчика, перед стартом игры содержит его код. Если игре важно содержимое «свободной» памяти, задайте `--reserve`.
- `--tiny`: без таймаутов (если нет диска — зависание), только дисковод и сторона, оставленные ПЗУ.

## 4a. Оболочка `run`: выбор программы на диске

`src/shell.asm` + `tools/mkshell.py`. Файл `run` — BASIC:

```
10 IF NOT USR VAL "PEEK 23627+256*PEEK 23628" THEN STOP
20 LOAD *"m";VAL "1";"??????????"
```

В переменных лежит заглушка на 18 байт и код (2,1 КБ, переносится на `#C000`). Код:
* берёт дисковод, с которого загружен `run` (из PIA), и геометрию из якоря, поэтому годится и для SD, и для DD;
* читает каталог и оставляет BASIC-файлы (тип 0 в 7-байтовом заголовке), кроме самого `run`;
* если программ нет, пишет «NO PROGRAMS», `USR` = 0 → `STOP`;
* если программа одна, запускает её сразу;
* если программ несколько, показывает меню: клавиши 1..9, A..Z; SPACE возвращает в BASIC;
* вписывает имя в строку 20, номер дисковода — в `VAL "1"`, и возвращает 1. Дальше программу загружает и запускает само ПЗУ Opus, как обычно.

Текст выводится прямо в экранную память шрифтом ПЗУ: `RST 16` после `CLS` в этом месте выдавал «Out of screen».

```bash
python tools/mkshell.py                          # build/run.opus: байты файла (с заголовком) для своих сборок
python tools/mkshell.py --add disk.opd game.dsk  # дописать run на готовые образы
```

На v1.2 `RUN` загружает `run`. На остальных ПЗУ эмулятор `RUN` не выполняет (см. §7), там работает `LOAD *"m";1;"run"`.

## 7. Что проверено и что нет

Проверено в эмуляторе на всех пяти ПЗУ, для SD и для DD (80×2×10×512): побайтная
точность (охранные зоны сразу за концом и перед началом каждого блока не меняются;
отрицательный тест подтверждает, что проверка ловит лишнюю запись), корректность чтения и записи (в том числе через границы дорожек и сторон, на двух
дисководах, с невыровненным буфером), `od_geom`, загрузка и сохранение по имени,
отсутствие диска (ошибка без зависания), все варианты моноблока. ПЗУ v1.2 само
загружает BASIC с DD-диска (читает якорь), и моноблок на DD работает.

**Не проверено на реальном железе:** скорость (эмулятор не моделирует вращение диска,
поэтому выигрыш от физического порядка секторов — расчётный), длительность таймаутов,
раскрутка мотора, скорость шага для конкретных дисководов. Форматирование не
реализовано и не проверялось: эмулятор не поддерживает Write Track.

**EXCOM 2.28 и 80-дорожечные дисководы.** У EXCOM таблица дисковода 1 по умолчанию —
80 дорожек × 2 стороны × 18 × 256 (`50 12 51 …`) с лишним 15-м байтом `02`. 40-дорожечный
диск он, судя по всему, читает **двойным шагом** (логическая дорожка t = физическая 2t),
как и нужно для 80-дорожечного дисковода с дискетой, отформатированной на 40-дорожечном.
Эмулятор двойной шаг не моделирует, поэтому в нём EXCOM не загружает с SD-диска ничего
дальше нулевой дорожки, даже с настоящего Astrum.opd. На SD-DS и DD всё проходит.
Наши процедуры двойной шаг **пока не умеют**: для такой связки на реальном железе
понадобится опция (искать физическую 2t без проверки, в регистр дорожки писать t).

Тестовая матрица моноблока с охранными зонами: 215+ случаев проходят на всех ПЗУ.
Не проходят только SD-раскладки с файлами вне нулевой дорожки на EXCOM (см. выше).
Ещё одно наблюдение: при `LOAD` BASIC-файла ПЗУ занимает рабочую область сразу за
программой (на DD — с буфером на 512 байт). Это происходит до запуска загрузчика,
поэтому для блоков безвредно, но память сразу за BASIC до загрузки не сохраняется.

Особенности ZX-M8XXX (v26.11.02), найденные по ходу:
0. DD-образы (80×2×10×512) эмулятор сам не принимает. Обвязка `zxharness.insert()` берёт геометрию из якорного сектора и подставляет её контроллеру: движок WD1770 у эмулятора общий, и с ней всё работает.
1. Геометрия (стороны/дорожки) хранится одна на контроллер и берётся из последнего вставленного образа. SS-диск в дисководе 1 рядом с DS-диском в дисководе 2 читается неверно.
2. ПЗУ v2.2, v2.22, EXCOM, QuickDOS (в том числе `opus.rom` по умолчанию): `RUN` без программы и `CAT 1` дают «C Nonsense in BASIC» или зацикливаются, а явный `LOAD *"m";1;"имя"` работает. Ошибка возникает при разборе оператора, который ПЗУ синтезирует в «стеке машинного кода» (CHKEND по `#050E` видит, что CH_ADD стоит не на конце оператора). v1.2 работает полностью.
3. Read Address возвращает текущий регистр сектора и размер 2 (512). Поэтому в эмуляторе автоопределение шага даёт «последовательно».
4. NMI по DRQ планируется с задержкой и в момент срабатывания не перепроверяется.
